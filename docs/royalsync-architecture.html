Section 1 Executive Summary & Vision
Royal Square Financial
Platform Architecture v1.0
The Core Problem Being Solved

Royal Square Financial currently operates as a traditional independent insurance broker — managing client portfolios, insurer relationships, compliance obligations, and policy administration largely through manual processes: paper files, spreadsheets, email threads, and telephone follow-ups. This creates risk (missed renewals, compliance gaps, lost documents), limits scale (adviser capacity is capped by manual workload), and delivers a poor client experience (no real-time visibility into their own financial position).

Platform Vision

RoyalSync is a multi-tenant SaaS platform that digitises and automates the complete lifecycle of independent insurance brokerage operations. Royal Square Financial is Tenant #1 — the platform is architected from day one to be licensed to other independent brokers across South Africa and, ultimately, across Africa and globally.

Regulatory Framework

POPIA

Protection of Personal Information Act — governs all personal data. Requires consent management, right to erasure (pseudonymisation), data breach notification within 72 hours, and data residency in South Africa.

FAIS

Financial Advisory & Intermediary Services Act — governs advice and intermediary services. Requires Record of Advice (ROA), commission disclosure, FNA (Financial Needs Analysis), 5-year document retention.

FICA

Financial Intelligence Centre Act — anti-money laundering and KYC obligations. Requires identity verification, PEP/sanctions screening, risk scoring, and suspicious activity reporting.

Platform Differentiation

Most broker management systems in South Africa are legacy desktop applications (e.g. Flexi, BrokerPoint) that were not designed for modern web, mobile, or multi-tenancy. RoyalSync is cloud-native, mobile-first, AI-assisted, and built to be licensed — giving Royal Square Financial a second revenue stream as the platform grows.

Section 2 Multi-Tenant Architecture
Royal Square Financial
Platform Architecture v1.0

Tenant Isolation Model

The platform uses a shared schema, row-level security model. All tenants share the same PostgreSQL database infrastructure, but every table has a tenant_id column and Row-Level Security policies enforce that no query can ever return rows from another tenant — at the database engine level, not the application layer.

┌─────────────────────────────────────────────────────────────┐ │ ROYALSYNC PLATFORM │ │ │ │ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ │ │ Royal Square│ │ Broker B │ │ Broker C │ │ │ │ Financial │ │ Cape Town │ │ JHB North │ │ │ │ tenant_id=1 │ │ tenant_id=2 │ │ tenant_id=3 │ │ │ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ │ │ │ │ │ │ │ └─────────────────┴─────────────────┘ │ │ │ │ │ ┌────────────▼────────────┐ │ │ │ PostgreSQL + RLS │ │ │ │ SET app.tenant_id = X │ │ │ │ Enforced at DB engine │ │ │ └─────────────────────────┘ │ └─────────────────────────────────────────────────────────────┘

Row-Level Security Implementation

-- On every table:
ALTER TABLE clients ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON clients
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- Set at the start of every request:
SET app.current_tenant_id = '<tenant_uuid>';
-- This is set by the API middleware from the JWT token.
-- No application code can bypass this — it is enforced at DB level.

Plug-and-Play Module System

Each tenant can enable or disable platform modules independently. Modules are rows in the tenant_modules table. When a module is disabled for a tenant, its navigation items disappear, its API endpoints return 403, and its data is excluded from all queries.

Offline & Network Resilience

All wizard flows auto-save every 3 seconds to the server. Uploaded files use chunked upload with resume capability — if the network drops mid-upload, the client selects nothing on return; the upload resumes from the last successful chunk. The client portal is a PWA with a service worker — clients can view their policies, documents, and claim status even when fully offline using cached data. Any actions taken offline (e.g. typing a message) are queued and submitted when connectivity returns.

Two-Person Sign-Off for Sensitive Operations

Critical Permission — Requires Two Super Admins

The following actions require a second super admin to approve before executing: delete or archive a client record, bulk export of client PII, modify another super admin's permissions, deactivate a user with active policies, reset MFA for any user, change bank mandate details without client consent flow, access audit log for a specific user (privacy protection). The first super admin initiates — the system sends an approval request to the second super admin. The action is held pending for 24 hours. Either super admin can cancel.

Individual Permission Overrides

On top of group-level permissions, a super admin can grant or revoke specific permissions for an individual user. Individual overrides are shown as checkboxes alongside each permission in the user's profile. An override does not change the group — it creates a delta record that is merged at permission resolution time.

Section 7 AI Systems
Royal Square Financial
Platform Architecture v1.0

Two Independent AI Systems

System A — Recommendation RAG

Where: Admin Portal — quote recommendation screen

Who triggers it: Client presses "I have a question" on a specific recommended insurer

Data source: Insurer's product document corpus (policy wording, benefits guide, claims guide)

Context: Scoped to one insurer. No cross-insurer mixing in one chat session.

System B — Client AI Assistant

Where: Client Portal — Insights tab + contextual inline triggers

Who triggers it: Client asks any question in their own app

Data source: Their own structured data (policies, claims, financials) + insurer documents

Context: Full client financial context. Cross-policy. Natural language.

RAG Architecture — Two-Stage Retrieval

USER QUESTION: "How much am I paying for Nomsa's cover?"

STAGE 1 — QUESTION ROUTING:
  Classifier identifies question type:
  → "financial_data"  — needs structured DB query
  → "policy_question" — needs vector search in documents
  → "hybrid"          — needs both

STAGE 2A — DB QUERY (for financial_data or hybrid):
  Backend extracts intent → generates parameterised SQL
  Example: SELECT SUM(premium_amount) FROM policies
           WHERE client_id = ? AND dependant_id = ? (Nomsa)
  Result: R 184/month — fully structured, no hallucination possible

STAGE 2B — VECTOR SEARCH (for policy_question or hybrid):
  Query embedded → search Pinecone / pgvector index
  Returns top-K chunks from relevant policy documents
  Each chunk tagged with: document_id, section, page, score

CONTEXT ASSEMBLY:
  Anonymised client context + DB results + retrieved chunks
  → Sent to LLM for response generation
  → LLM returns JSON response (not raw text)
  → Backend stores full conversation with chunk citations

PII PROTECTION:
  Never sent to LLM: full name, ID number, bank account,
  full address, policy number, beneficiary details
  The LLM receives: [CLIENT], [SPOUSE], [POLICY_A], [POLICY_B]
  The backend maps these placeholders back to real values
  before displaying to the client

Regulatory Compliance of AI Conversations

Every AI conversation is stored permanently with: full message history, source chunks cited per response, LLM model version and temperature used, conversation state at each turn, and client/adviser identifiers. This record is retrievable for FAIS regulatory audit. The AI is explicitly prohibited from giving advice — it answers questions about what a policy says or what data shows. Advice decisions remain with the human adviser.

Each insurer has a different integration method — some have REST APIs, some use SOAP/XML, some accept SFTP file drops, some still work via email. Message Reliability — Queue & Retry

Happy Path

  1. Request placed in SQS queue
  2. Worker picks up & sends to insurer
  3. 200 OK received
  4. Response normalised & stored
  5. Admin notified — quote arrived
  6. Integration audit log entry created

Failure Path

  1. Request placed in SQS queue
  2. Worker picks up & sends to insurer
  3. Error or timeout received
  4. Exponential backoff retry (1m, 5m, 30m)
  5. After 3 failures → dead-letter queue
  6. Super admin alerted. Manual intervention flow opens.

In-App Search Engine

Universal search is available from every screen via Cmd+K / Ctrl+K or the search icon in the top bar. Results are categorised into three types:

Navigation Results

Take the user to any screen or section of the app. Indexed locally — returns in under 50ms. No server call needed.

e.g. typing "claims" → shows Claims section link

Data Results

Find specific records — policies, clients (admin), claims, documents, goals. Fuzzy matched. Handles typos and partial IDs.

e.g. admin types "dlamni" → finds "Dlamini"

Action Results

Trigger actions directly from search without navigating. e.g. "report accident", "upload document", "contact adviser".

e.g. typing "bank" → shows "Update bank details" action

Colour Token System — All AI JSON Responses Are Colour-Mode Aware

The AI response JSON uses semantic colour tokens ("color_scheme": "red"), never hex values. The UI renderer maps each token to the correct actual colour for the current user's colour blind mode. A user with deuteranopia sees a different actual colour for "red" — but the semantic meaning (danger/error) is always conveyed by both colour AND an icon, so no information is ever lost for any user.

Technology Stack — Cloudflare-Native Architecture

Architecture Philosophy

Cloudflare Workers handles all edge concerns (routing, auth, rate limiting, caching, file storage, queues). Node.js + Hono (deployed on Workers) serves the business logic API endpoints. FastAPI (Python) handles AI/RAG processing, document parsing, and data transformation — deployed as a Worker service or container. React + TypeScript on all four portals, served from Cloudflare Pages with edge-side rendering.

Cloudflare Workers — What Each Worker Does

WorkerBindings UsedResponsibility
auth-workerKV (sessions), D1 (user lookup cache)Validates JWT on every request. Sets tenant context. Blocks unauthenticated requests at edge before they reach the API — zero cost on origin.
api-worker (Hono)KV, Hyperdrive (→PostgreSQL), D1, R2, Queues, AI GatewayAll business logic endpoints. Routes requests to appropriate handlers. Returns JSON. WebSocket upgrade for real-time.
upload-workerR2 (storage), KV (upload state)Handles chunked file uploads directly to R2. Tracks upload progress in KV. Supports resume on network drop. Validates file type and size.
notification-workerQueues (consumer), KV (dedup)Consumes notification jobs from Cloudflare Queues. Routes to WhatsApp API / Resend (email) / Twilio (SMS). Dedup via KV to prevent double-send.
integration-workerQueues (consumer), KV (state), R2 (docs)Consumes insurer integration jobs. Calls FastAPI service for insurer-specific normalisation. Handles retry and dead-letter. Stores responses in R2.
search-workerHyperdrive, D1 (index cache)Handles admin full-text search across clients, policies, claims. Uses pg_trgm on PostgreSQL. Caches common queries in D1.
